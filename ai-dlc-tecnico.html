AI-DLC na prática: um chatbot RAG da intenção ao deploy, com humano no loop

Um estudo de caso técnico de ponta a ponta. Construímos um assistente conversacional que responde a partir de uma base de conhecimento própria — RAG + Foundation Model + Guardrails na AWS — governado por um ciclo AI-DLC com Jira e GitHub. Este curso documenta as decisões, o código e, principalmente, os problemas reais que só aparecem quando se constrói de verdade.

MÓDULO 01O que é AI-DLC (e por que arquiteto deve se importar)

AI-DLC (AI-Driven Development Lifecycle) é a metodologia publicada pela AWS em julho de 2025, com os workflows abertos como awslabs/aidlc-workflows em novembro. A IA rascunha planos, código, testes e configuração de infraestrutura; humanos validam cada passo antes da execução prosseguir. O papel do dev migra de escrever código para dirigir e validar o que foi gerado.

A sequência de fases não muda. Requisitos, design, código e deploy continuam na mesma ordem do SDLC. O que muda é quem rascunha cada artefato, quão rápido o ciclo gira e onde a atenção humana é gasta.

A diferença que importa para um arquiteto não é "a IA escreve código". É que o conhecimento arquitetural fica materializado em artefatos (steering, specs), a IA respeita esses artefatos como contrato, e o humano permanece no ponto de controle — o human-in-the-loop não é opcional, é estrutural.

Três fases, com Operations realimentando o começo

┌──────────────── realimenta ─────────────────┐ │ │ ▼ │ ┌────────────────────────────┐ ┌──────────────────────┐ ┌────────┴───────────┐ │ INCEPTION │ │ CONSTRUCTION │ │ OPERATIONS │ │ intenção → requisitos │─▶│ arquitetura, domínio │─▶│ deploy, telemetria │ │ → unidades de trabalho │ │ código, testes │ │ incidentes, evals │ │ │ │ │ │ │ │ 👥 Mob Elaboration │ │ 👥 Mob Construction │ │ 👤 operação │ └────────────────────────────┘ └──────────────────────┘ └────────────────────┘ cadência: BOLT — ciclo de horas ou dias, não de semanas

O recorte que o Kiro implementa bem, e que este curso documenta em profundidade, é o ciclo de specs dentro da Construction:

┌─────────────────────────────────────────────────────┐ │ │ ▼ │ INTENT ──▶ REQUIREMENTS ──▶ DESIGN ──▶ TASKS ──▶ CODE ──▶ DEPLOY │ │ │ │ │ │ └── 👤 ──────┴──── 👤 ─────┴─── 👤 ───┴── 👤 ───┴── 👤 ──┘ gate de aprovação humana em cada transição
Insight para líderesO ganho real do AI-DLC não é velocidade de digitação — é rastreabilidade e governança. Cada linha de código rastreia até uma task, que rastreia até um requisito aprovado. A trilha de auditoria faz parte da definição do método, não é subproduto.
A trilha só existe se você a fecharRastrear task → requisito é a parte fácil. Para o artefato ser auditável de verdade falta registrar qual modelo, qual versão e qual revisão da spec geraram aquele código. Trocar de modelo por variável de ambiente (módulo 05) é portabilidade, e ao mesmo tempo um buraco de auditoria: fixe o modelId com versão e registre-o no PR.

Não confunda a ferramenta com o métodoSpec-driven development com gate de aprovação já existia antes do AI-DLC, e é o que o Kiro entrega. O que distingue a metodologia são as três peças acima: cadência de bolt, validação coletiva e rigor adaptativo. O módulo seguinte trata delas; sem isso, o que resta é um assistente melhor, não uma metodologia diferente.

MÓDULO 02Mob Elaboration e Mob Construction

Esta é a peça central do AI-DLC e a que mais se perde quando se olha só para a ferramenta. O método não pede que o agente proponha e alguém aprove depois, sozinho, num Pull Request assíncrono. Pede que as pessoas certas estejam juntas e ao mesmo tempo enquanto o agente propõe.

Por que síncrono, e por que isso não é preferência de gestão

A premissa do método é que o gargalo mudou de lugar. Rascunhar ficou barato; validar virou o caro. Se o gargalo é validar, revisão assíncrona é a pior arquitetura possível: cada rodada de dúvida custa horas de espera, o contexto se perde entre elas e a fila cresce mais rápido que a vazão. Com o time na mesma sessão, uma ambiguidade que apareceria na semana seis morre em minutos.

MOB ELABORATION (Inception) MOB CONSTRUCTION (Construction) ──────────────────────────── ────────────────────────────────── agente interroga a intenção agente propõe arquitetura e plano │ │ ▼ ▼ 👥 time valida AS PERGUNTAS 👥 time verifica O PLANO (produto, QA, negócio, dev) (dev sênior, arquiteto) │ │ ▼ ▼ agente deriva requisitos + agente gera código + testes unidades de trabalho │ │ ▼ ▼ 👥 time revisa o gerado 👥 time aprova (versionado) │ │ └──▶ próximo laço (minutos) └──────────▶ vira o backlog do bolt

Mob Elaboration — na Inception

O time examina em conjunto as perguntas que o agente levanta sobre a intenção de negócio, antes das respostas dele. Só então valida os requisitos e as unidades de trabalho derivadas.

  • Quem está na sala: time multifuncional. Produto, análise de negócio e QA junto com devs. A IA prospera com especificidade, e cada área carrega uma fatia do contexto que falta.
  • O artefato de saída: requisitos e unidades de trabalho aprovados de forma versionada, não consenso verbal.
  • Sinal de que funcionou: alguém discordou de alguma coisa. Se a sessão inteira foi "sim, ok", ninguém leu.
Elaboração dirigida por perguntasO passo que quase todo material omite: antes de propor qualquer coisa, o agente interroga a intenção vaga. Um agente que devolve dez perguntas incômodas sobre o pedido está fazendo o trabalho certo — é ali que aparece, no dia um, a ambiguidade que normalmente vira retrabalho na semana seis.

Mob Construction — na Construction

Mesmo formato aplicado ao plano técnico, num laço apertado: o agente propõe, humanos verificam, o agente gera, humanos revisam, repete. A sessão termina quando a unidade de trabalho está integrada, não quando o relógio bate.

A cadência: bolt no lugar do sprint

Um bolt é o ciclo de trabalho do AI-DLC: horas ou dias, em que o time valida um plano proposto pelo agente, o agente executa e o resultado é revisado. Se a unidade de trabalho não cabe numa sessão, ela está grande demais e precisa ser fatiada antes de começar.

PráticaSDLCAI-DLC
CicloSprint de 1 a 4 semanasBolt de horas ou dias
Unidade de escopoÉpico, históriaUnidade de trabalho
Momento da validaçãoCode review assíncrono, dias depoisAo vivo, no mesmo laço da geração
Quem validaUm revisor por PRO mob, com as áreas necessárias

Custo real: atenção sênior

O que não aparece no keynoteMob exige as pessoas mais experientes, juntas, síncronas, por horas. O método gasta menos com digitação e mais com atenção sênior. Um líder que lê "menos tarefa mecânica, mais julgamento" e não lê a segunda metade dimensiona o time errado. Se você tem um arquiteto para cinco squads, o gargalo do AI-DLC não é a IA, é ele.

Anti-padrões

  • Mob de fachada: rodar a sessão e deixar a validação real para o PR assíncrono da semana seguinte. Paga-se o custo dos dois modelos sem o benefício de nenhum.
  • Mob só de devs: a elaboração perde exatamente o contexto que ela existe para capturar.
  • Bolt com escopo de sprint: se a sessão não fecha em horas ou dias, a unidade de trabalho foi mal fatiada. Fatie antes, não no meio.
  • Aprovar sem discordar: gate que nunca reprova nada não é gate, é carimbo.

Rigor adaptativo

O workflow analisa se a base é nova ou existente, avalia complexidade e decide quais estágios valem a pena. Correção simples de bug pula planejamento e vai direto para geração de código; feature complexa recebe análise de requisitos, design arquitetural e teste detalhado.

Correção de uma regra da primeira versão deste curso"Gate humano em cada transição de fase, não pule" contradiz um valor fundamental do método. Workflow tamanho único, que força todo projeto pela mesma sequência rígida, é um dos três problemas que a metodologia se propõe a resolver. A formulação correta: o gate é obrigatório em cada transição que o trabalho exigir, e escolher quais estágios se aplicam é ela própria uma decisão humana, tomada no início.
O que este estudo de caso não exercitaTudo que vem a seguir foi construído por uma pessoa só. O material documenta a Construction com profundidade real, incluindo os erros, e não exercita Inception coletiva, cadência de bolt nem rigor adaptativo. Vale ler os módulos seguintes com essa delimitação em mente.

MÓDULO 03Arquitetura de referência

O sistema é um chatbot RAG: recebe uma pergunta, recupera contexto de uma base de conhecimento própria e gera a resposta com um LLM. Arquitetura serverless com três serviços do Amazon Bedrock. Toda a infra em região única.

┌──────────┐ HTTPS + x-api-key ┌──────────────┐ ┌────────────────────────┐ │ Cliente │ ─────────────────────▶ │ API Gateway │ ───▶ │ Lambda (Python 3.12) │ │ (front) │ + CORS restrito │ (REST, key) │ │ handler → orquestrador │ └──────────┘ └──────────────┘ └───────────┬────────────┘ │ ┌───────────────────────────────────────────────────────┼──────────────────┐ ▼ ▼ ▼ ┌──────────────────┐ ┌──────────────────────┐ ┌──────────────────┐ │ Bedrock Guardrail│ │ Bedrock Knowledge Base│ │ Bedrock (Converse)│ │ ApplyGuardrail │ │ Retrieve (RAG) │ │ + guardrailConfig │ │ (pré-filtro) │ │ │ │ (entrada e saída) │ └──────────────────┘ └───────────┬──────────┘ └──────────────────┘ ▼ ┌──────────────────────┐ │ OpenSearch Serverless │ ← vector store gerenciado └──────────────────────┘ Observabilidade transversal: CloudWatch Logs (JSON) + Métricas (EMF) + X-Ray
Pré-filtro e guardrail da chamada não são a mesma coisaPassar guardrailConfig no converse aplica o guardrail à entrada e à saída daquela chamada. Se você quer barrar a pergunta antes de gastar um Retrieve e um converse, precisa de uma chamada explícita a ApplyGuardrail na borda. São decisões diferentes, com custo diferente: o pré-filtro economiza a rodada inteira em pergunta fora de escopo.

Fluxo de uma requisição

  1. POST /chat com a pergunta do usuário (JSON).
  2. Lambda valida o payload e monta a query de recuperação.
  3. Retrieve na Knowledge Base (RAG) → trechos relevantes dos documentos indexados.
  4. Se não há contexto, o system prompt instrui a responder "sem informação suficiente". Note que isso é instrução, não garantia arquitetural: só um conjunto de avaliação mostra com que frequência o modelo obedece.
  5. InvokeModel (via API Converse) com contexto + guardrail aplicado.
  6. Log estruturado + métricas + trace X-Ray.

MÓDULO 04Specs & steering — o contrato do projeto

A base do AI-DLC no ecossistema Kiro são dois diretórios versionados: .kiro/steering/ (regras permanentes) e .kiro/specs/ (o ciclo de uma feature).

Steering — regras que a IA sempre respeita

  • product.md — o que o produto faz, regras de negócio, escopo/fora-de-escopo
  • tech.md — stack, região, restrições de conta, padrões de qualidade
  • structure.md — layout do repo, convenções de branch/PR/commit
  • governanca.md — CI obrigatório, proteção de branch, gates

Specs — o ciclo de uma feature (3 fases + aprovação)

Requisitos em formato EARS (Easy Approach to Requirements Syntax) — cláusulas testáveis:

# requirements.md — critério de aceite EARS
QUANDO o usuário enviar uma pergunta sobre o domínio,
O SISTEMA DEVE responder com base nos documentos recuperados.

QUANDO a base de conhecimento não cobrir o assunto,
O SISTEMA DEVE dizer que não tem informação suficiente,
em vez de inventar.

Cada fase termina num checkbox de aprovação. O design só começa quando os requisitos são aprovados; as tasks só quando o design é aprovado. As tasks viram os cards do Jira 1:1.

A spec é a fonte da verdade, e isso tem consequência com mais de um devO agente regenera código a partir da spec. Se dois devs editam specs em branches paralelos, o conflito não é textual, é semântico: o Git faz merge limpo de duas specs que se contradizem e o CI fica verde enquanto dois agentes constroem coisas incompatíveis. O anteparo é separar PR de spec de PR de implementação, e mesclar specs, contratos e schemas no main antes de qualquer branch de código nascer. Steering merece o mesmo tratamento: alterar .kiro/steering/ muda o comportamento de todos os agentes ao mesmo tempo, então vale CODEOWNERS e revisão dupla, não o gate de um ajuste de CSS.
PadrãoRequisitos em EARS não são burocracia — são asserts em linguagem natural. Cada cláusula "O SISTEMA DEVE..." deve virar um teste, e rastreabilidade requisito→design→task→código→teste fecha o loop.
O loop só fecha se houver mecanismo"Cada cláusula vira um teste" não acontece sozinho. Sem um identificador de requisito citado no nome ou no docstring do teste, a rastreabilidade é aspiração, não propriedade verificável. Convenção mínima: REQ-04 na cláusula EARS e test_req_04_sem_contexto_responde_nao_sei no teste, com um job de CI reclamando de requisito sem teste correspondente.

MÓDULO 05CI/CD: qualidade, evals e sync com o Jira

A ponte Jira↔GitHub foi feita com GitHub Actions + a API REST do Jira (stdlib pura, sem dependências), disparada por eventos de Pull Request.

O job que faltava: evals do RAG

Conjunto de perguntas de referência versionado no repo, rodando a cada PR. Sem ele, trocar o modelo, mudar o chunking ou recalibrar o guardrail quebra o comportamento sem nenhum sinal vermelho — exatamente o risco que a v4 do guardrail criaria em cima da v3 calibrada à mão.

# evals/golden.yaml — versionado junto com o código
- id: REQ-04-sem-cobertura
  pergunta: "qual a política de férias da concorrência?"
  espera: recusa            # não deve inventar
- id: REQ-01-caminho-feliz
  pergunta: "como solicito reembolso?"
  espera_trecho_de: "politica-reembolso.md"   # fundamentação
  contem: ["prazo", "formulário"]
- id: GUARD-falso-positivo
  pergunta: "o reembolso cobre despesa médica da viagem?"
  espera: resposta          # domínio legítimo, NÃO bloquear

Três métricas bastam para começar: taxa de recuperação (o trecho certo apareceu no top-k), fundamentação (a resposta se apoia no que foi recuperado) e guardrail nos dois lados (falso positivo e falso negativo). O gate reprova em regressão, não em nota absoluta.

Gotcha realO gitleaks-action falhou com 403 "Resource not accessible by integration" — o GITHUB_TOKEN padrão não lê PRs sem permissão explícita. Solução: adicionar permissions: {contents: read, pull-requests: read} ao workflow.

MÓDULO 06Bedrock: Knowledge Base + Foundation Model + Guardrails

Knowledge Base (RAG)

Criar uma KB via API pura é frágil (7 recursos: role, 3 políticas OpenSearch, índice vetorial, KB, data source). O índice vetorial exige uma chamada HTTP assinada (SigV4) ao endpoint aoss. Solução prática: "Quick create vector store" no console, que cria coleção + índice automaticamente. Depois, ingira os documentos (S3 → Sync) e o runtime só chama Retrieve:

# src/bedrock_kb.py
resp = client.retrieve(
    knowledgeBaseId=kb_id,
    retrievalQuery={"text": consulta_do_usuario},
    retrievalConfiguration={"vectorSearchConfiguration": {"numberOfResults": 5}},
)
Documentos autocontidosPara RAG, prefira documentos-fonte cujas seções sejam autocontidas (repetem o contexto necessário). O chunking automático do Bedrock lida melhor com isso, e cada trecho recuperado faz sentido isolado.
Citação não vem de graça neste caminhoCom retrieve + converse separados, você recebe os trechos com metadados e monta a atribuição você mesmo: nada garante que o modelo referencie o trecho certo. Se a promessa ao usuário é "resposta com fonte", carregue location e score de cada trecho até a resposta e valide isso nos evals. A alternativa pronta é RetrieveAndGenerate, que devolve citações estruturadas em troca de menos controle sobre o prompt.

Foundation Model — use a API Converse

Decisão de arquitetura chave: em vez de InvokeModel com o payload específico de cada modelo (Claude ≠ Nova ≠ DeepSeek), usamos a API Converse — formato unificado. Trocar de modelo vira mudar uma string.

# src/bedrock_fm.py — agnóstico de modelo
resp = client.converse(
    modelId=model_id,                       # deepseek, claude, mistral, nova…
    system=[{"text": SYSTEM_PROMPT}],
    messages=[{"role": "user", "content": [{"text": prompt_com_contexto}]}],
    inferenceConfig={"maxTokens": 900, "temperature": 0.3},
    guardrailConfig={"guardrailIdentifier": gid, "guardrailVersion": ver},
)
Por que ConverseDesacopla o serviço do fornecedor do modelo. O mesmo código serve Claude, DeepSeek, Mistral e Nova. Em produção, isso é portabilidade de modelo sem refatoração.

Guardrails

Guardrail do Bedrock aplicado nas duas pontas: tópicos negados (manter o bot no domínio), filtros de conteúdo (HATE/SEXUAL/VIOLENCE) e PII. A calibração é a parte difícil (ver módulo de armadilhas).

Guardrail é filtro probabilístico, não controle de acessoEle reduz resposta fora de escopo; não substitui autorização nem fronteira de dado. Se um documento não pode ser visto por um perfil de usuário, isso se resolve com filtro de metadado na recuperação e permissão, nunca confiando que o classificador vai barrar.

MÓDULO 07Segurança & as travas da conta gerenciada

Contas AWS gerenciadas (ex.: a "nova experiência AWS") podem ter SCP/RCP gerenciadas e não editáveis. Isso impõe restrições que mudam decisões de arquitetura:

Restrição estruturalPOST anônimo pode ser bloqueado. Endpoint público sem autenticação (API Gateway sem auth, ou Lambda Function URL AuthType=NONE) retorna 403 na borda — antes de chegar ao seu código. Se a RCP não é editável, não há como contornar por policy: mude a estratégia de auth.

Matriz de autenticação para front-end

Anônimo + CORSNão (403)—Inviável em conta travada

Chave nunca no clientePara produção, o padrão correto é um proxy no seu backend (Netlify/Vercel Function, ou uma API própria) que guarda a credencial e chama o serviço por trás. O navegador nunca vê o segredo. API Key no front só se justifica para conteúdo não-sensível de baixo tráfego, com rate limit.

CORS que não mascara erros

Sutileza crítica: um 403 de API Key gerado pelo API Gateway não passa pela Lambda, então não tem header CORS — e o navegador reporta "erro de CORS" mascarando o 403 real. Solução: GatewayResponse com CORS nas respostas de erro.

# template.yaml — erros do API GW respondem com CORS
GatewayResponse4xx:
  Type: AWS::ApiGateway::GatewayResponse
  Properties:
    ResponseType: DEFAULT_4XX
    ResponseParameters:
      gatewayresponse.header.Access-Control-Allow-Origin: "'https://seu-dominio.com'"
Regra de ouro CORSO preflight OPTIONS NUNCA deve exigir API Key — o navegador não envia a chave no preflight. Marque ApiKeyRequired: false só no OPTIONS.

MÓDULO 08Observabilidade sem custo de API

Métricas via EMF (Embedded Metric Format): a Lambda apenas imprime um JSON com bloco _aws no stdout, e o CloudWatch extrai as métricas automaticamente — sem chamada PutMetricData (sem custo de API, sem latência).

# src/observability.py — métrica EMF
emf = {
  "_aws": {
    "Timestamp": int(time.time()*1000),
    "CloudWatchMetrics": [{
      "Namespace": "ChatbotRAG",
      "Dimensions": [["service"]],
      "Metrics": [{"Name": "LatenciaMs"}],
    }],
  },
  "service": "chatbot-rag",
  "LatenciaMs": 812.0,
}
print(json.dumps(emf))  # CloudWatch faz o resto

Complementado por logs JSON estruturados (um evento por linha, ex.: latência, se houve contexto recuperado, se o guardrail bloqueou) e X-Ray (Tracing: Active no template) para o trace distribuído das chamadas Bedrock.

MÓDULO 09Armadilhas reais (o que só aparece construindo)

Este é o módulo mais valioso para um arquiteto: os problemas que nenhum tutorial menciona.

1. Deprecações de API silenciosas

O endpoint /rest/api/3/search do Jira foi removido (HTTP 410 Gone) → migrar para /rest/api/3/search/jql. Actions em Node 20 deprecadas → checkout@v5, setup-python@v6. Lição: automações contra APIs externas precisam de manutenção contínua.

2. Localização quebra automação

Um board Jira em português tem transições A fazer / Fazendo / Em análise / Feito. Um script que tentava "Done" falhava silenciosamente. Lição: não hardcode nomes de transição em inglês; descubra-os via API.

3. Model access gate

Alguns modelos (ex.: Anthropic) exigem preencher um formulário de caso de uso na conta antes de responder — retornam ResourceNotFoundException: Model use case details have not been submitted. Contorno sem bloquear: usar a API Converse + um modelo já liberado, trocando o ID sem mudar código.

4. Guardrail: falso positivo por definição ampla

Definir tópico negado por exclusão ("tudo que não é o meu domínio") faz o classificador bloquear o próprio domínio — perguntas legítimas vêm barradas. A calibração passou por 3 versões:

VersãoDefiniçãoResultado
v1"tudo fora do domínio" (exclusão)Bloqueia o domínio legítimo
v2genérica demaisNão bloqueia o que devia
v3categorias específicas (finanças, código, saúde) + exemplosCalibrado
Lição de guardrailDefina tópicos negados por categorias positivas e específicas com exemplos concretos, nunca por exclusão do domínio. E teste os dois lados: falso positivo (bloqueia o certo) e falso negativo (deixa passar o errado).

MÓDULO 11Checklist do arquiteto

Antes de começar

  • Mapeie as restrições de conta (SCP/RCP) — elas mudam a arquitetura, não são detalhe
  • Steering primeiro: produto, tech, estrutura, governança versionados
  • Model access: confirme quais modelos estão invocáveis (não só listados)

No ciclo

  • Escolha o rigor antes: bug simples vai direto ao código; feature nova recebe o ciclo inteiro. Decidir quais estágios se aplicam é a primeira decisão humana
  • Gate humano obrigatório em cada transição que o trabalho exigir — workflow tamanho único é o problema, não a virtude
  • Inception em mob, com produto e QA na sala, não só devs
  • Requisitos EARS com ID → cada cláusula vira teste rastreável por identificador
  • Com um dev: 1 task = 1 card = 1 branch = 1 PR. Com vários: spec e contratos mesclados no main antes de qualquer branch
  • API agnóstica de modelo (Converse) desde o dia 1, com modelId versionado e registrado no PR

Segurança & operação

  • Segredo nunca no cliente — proxy no backend para produção
  • Permissão IAM mínima por recurso (não por serviço)
  • CORS nos erros também (GatewayResponse), senão o browser mascara 403
  • Guardrail: tópicos por categoria específica; teste falso positivo E negativo
  • Observabilidade barata (EMF + logs JSON + X-Ray) desde o início
  • Guardrail é filtro, não autorização — dado restrito se resolve com filtro de metadado e permissão
  • Golden set de evals como gate de PR, desde o primeiro card
  • FinOps: vector store (OpenSearch Serverless) cobra 24/7 — planeje teardown. Em baixo volume ele supera a inferência; com tráfego real a conta se inverte

Estudo de caso: chatbot RAG — assistente conversacional que responde a partir de uma base de conhecimento própria. Stack: AWS Lambda + API Gateway + Bedrock (Knowledge Base + Foundation Model via Converse + Guardrails) + SAM, governado por Kiro (steering/specs/tasks) com CI/CD Jira + GitHub.
