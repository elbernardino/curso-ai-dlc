MÓDULO 01

O que é AI-DLC e por que testar

No ciclo de desenvolvimento tradicional (SDLC), a pessoa escreve a especificação, o código, os testes e configura a esteira. A IA entra como autocomplete, ajudando linha a linha.

No AI-DLC (AI Development Life Cycle) a ordem muda. Você descreve a intenção em linguagem natural. A IA propõe a especificação, os testes e o código. Seu trabalho passa a ser revisar, corrigir o rumo e aprovar. O papel humano sobe de digitar para dirigir.

Por que este projeto existiu
O objetivo não era o produto. Era testar o ciclo AI-DLC de ponta a ponta em algo real, não um protótipo de slide: uma aplicação de IA em produção, com todos os componentes que um sistema sério precisa ter.

O que foi construído

Um chatbot fundamentado em uma knowledge base, publicado como uma API no final. O usuário envia uma pergunta, o sistema recupera o contexto relevante de uma base de conhecimento própria (RAG), gera a resposta com um modelo de linguagem, aplica um filtro de segurança e devolve uma resposta fundamentada, não inventada.

É o padrão de arquitetura mais comum em aplicações de IA corporativa hoje: um assistente que responde com base nos documentos e regras da própria empresa, exposto como um serviço que outros sistemas consomem.

IDE: Kiro IA: Amazon Bedrock Compute: Lambda + API Gateway Fluxo: Jira + GitHub IaC: AWS SAM Região: sa-east-1
MÓDULO 02

Preparação: conta AWS, identidade e credenciais

Antes de qualquer código, a base. A conta usada é da nova experiência AWS (login por provedor social, recursos organizados em projeto, região única definida pelo endereço de contato).

Passos

  1. Instalação da AWS CLI v2 oficial e do Agent Toolkit for AWS, que conecta um servidor MCP da AWS ao Kiro.
  2. Login por aws login com passkey no navegador, sob um perfil dedicado.
  3. Criação de um usuário IAM administrador para o dia a dia, com a conta root guardada só para emergências.
  4. Um orçamento de custo (AWS Budgets) com alertas por e-mail, como rede de proteção contra surpresa na fatura.
Erro real e correção
O primeiro aws login deu 400 Bad Request. A causa era a região: na nova experiência AWS, o login precisa apontar para a região onde o projeto foi criado. Ajustada a região, o login passou. Lição: a região não é preferência, é onde o projeto vive.
Princípio de segurança
Root só para emergência. Usuário IAM para o dia a dia. Credenciais temporárias (válidas 12h) em vez de chaves estáticas de longo prazo. Isso limita o estrago se algo vazar.
MÓDULO 03

O ambiente: Kiro, steering e specs

O Kiro dirige o ciclo AI-DLC por dois artefatos versionados: steering (regras e contexto permanente do projeto) e specs (a especificação de cada funcionalidade, com requisitos, design e tarefas).

Steering: o contexto que não muda

Arquivos em .kiro/steering/ guardam as decisões estáveis: as regras do projeto, a configuração do Jira, a política de governança. A IA lê isso em todo trabalho, então ela nunca esquece o contexto.

Specs: a intenção que vira plano

Cada funcionalidade nasce como uma spec. Você descreve a intenção, a IA propõe requisitos, desenho técnico e uma lista de tarefas. Você revisa e aprova antes de uma linha de código ser escrita.

Ganho
A especificação passa a existir como artefato versionado desde o primeiro dia, em vez de morar na cabeça de alguém. Quem entra no projeto depois lê a spec, não adivinha.
MÓDULO 04

Jira e GitHub: o fluxo de trabalho

O trabalho foi quebrado em cards no Jira e cada card virou um Pull Request no GitHub. A integração entre os dois foi feita com GitHub Actions.

Como o ciclo fecha sozinho

  • Seed de cards: um workflow que criou os cards iniciais de uma vez, a partir de um script.
  • Sync Jira-GitHub: a cada Pull Request aprovado e mesclado, o card correspondente se move sozinho para concluído e recebe um comentário automático com o link.
Detalhe que quebrou e foi corrigido
O board do Jira estava em português. O workflow tentava mover o card para "Done" e falhava, porque a coluna se chamava "Feito". Corrigido o nome da transição, o sync passou a funcionar. Lição: a automação precisa falar o idioma exato do board.
Segredos, do jeito certo
As credenciais do Jira (URL, e-mail, API token) nunca foram para o código. Ficaram como secrets no GitHub, lidas só em tempo de execução pela esteira. Nenhum segredo em texto puro no repositório.
MÓDULO 05

CI/CD: a esteira que protege a main

Nenhuma mudança entrou na branch principal sem passar por revisão e por uma esteira automática. A cada Pull Request, o CI roda:

  • ruff: análise de estilo e qualidade do código Python.
  • pytest: a suíte de testes automatizados (terminou com 28 testes).
  • gitleaks: varredura de segredos vazados no código.
  • sam validate: validação do template de infraestrutura.

Só entra quem está verde nas quatro verificações.

Limite de plataforma
A proteção nativa de branch (impedir push direto na main pelo GitHub) exige plano pago em repositório privado. A solução foi "proteção por convenção": governança documentada, o próprio ambiente já bloqueia push direto na main, e o CI roda em todo PR. Nem toda trava precisa ser um recurso pago, algumas são disciplina de processo.
MÓDULO 06

Amazon Bedrock: modelo, knowledge base e guardrail

A camada de IA do chatbot usou três recursos distintos do Bedrock, cada um com um papel claro.

RecursoPapel
Foundation ModelGera a resposta do chatbot. Via API Converse, agnóstica de modelo.
Knowledge Base (RAG)Fundamenta a resposta nos dados reais da base, para o modelo não inventar.
GuardrailImpede o chatbot de responder fora do escopo (finanças, código, saúde).
Por que RAG importa num chatbot
Um modelo de linguagem sozinho responde com o que "lembra" do treino, e às vezes inventa. Com uma knowledge base, o chatbot primeiro busca o trecho relevante na base própria e só então responde, citando a fonte. É a diferença entre um chatbot que chuta e um que responde com base nos seus documentos.
O guardrail levou três versões
A v1 bloqueava tudo, porque definia o tópico proibido por exclusão. A v2 ficou permissiva demais. A v3 acertou, calibrada com categorias específicas e sem falso positivo. Calibrar comportamento de IA é julgamento humano, e a IA não substitui isso.
Escolha do modelo
O Claude exigia preencher um formulário de caso de uso da Anthropic. Para não travar, a integração usou a API Converse (agnóstica de modelo) com um modelo liberado sem formulário. Trocar de modelo passou a ser mudar uma variável, não reescrever a integração.
Atenção a custo
A knowledge base usa OpenSearch Serverless, que cobra por capacidade 24 horas por dia enquanto existir, independente de uso. É o maior custo da arquitetura. Lambda e API só cobram por uso. Lição: em IA, o armazenamento vetorial custa mais que a inferência no dia a dia.
MÓDULO 07

Da spec ao código: o ciclo card a card

Com a base pronta, o desenvolvimento virou um ritmo repetido, card a card. Os cards seguiram a construção natural de um chatbot com RAG: ingerir a base de conhecimento, recuperar o contexto, chamar o modelo, aplicar o guardrail, expor como API.

  1. Pegar o card no Jira.
  2. A IA propõe o código e os testes a partir da spec.
  3. Revisar, ajustar, abrir o Pull Request.
  4. O CI roda as quatro verificações.
  5. Aprovar e mesclar. O card se move para concluído sozinho.

Foram 15 Pull Requests até a aplicação ficar pronta. Cada um passou pela mesma esteira.

A validação deixou de competir com o prazo
Os testes vieram junto com o código, a partir da mesma spec. Terminamos com 28 testes, não por disciplina extra, mas porque gerar o teste custou o mesmo que gerar a função. No modelo tradicional, o teste é o primeiro item cortado quando o prazo aperta. Aqui não.
MÓDULO 08

Deploy em produção com AWS SAM

A infraestrutura foi definida como código com AWS SAM (um template versionado descreve a Lambda, a API e as permissões). O deploy em produção foi feito por uma pessoa, de forma deliberada.

sam validate      # a esteira valida o template em todo PR
sam build         # empacota a função
sam deploy        # publica a stack em produção
Decisão consciente
Automatizar a geração de código é uma coisa. Colocar no ar é uma decisão que se mantém sob controle humano. Gerar rápido não significa publicar sem revisar.

Resultado: a Lambda e a API do chatbot rodando em produção, testadas ponta a ponta. Recebe a pergunta, recupera contexto da knowledge base, chama o foundation model, aplica o guardrail e devolve uma resposta fundamentada.

MÓDULO 09

Publicar a API: a trava da conta e a solução

Aqui apareceu a restrição mais instrutiva do projeto. A ideia inicial era expor a API do chatbot publicamente, protegida só por CORS restrito ao domínio que a consome.

O POST anônimo retornou 403
A conta da nova experiência AWS tem políticas de segurança gerenciadas (SCP/RCP) que bloqueiam endpoints públicos anônimos por design, e essas políticas não são editáveis. O CORS puro não resolve, porque CORS é uma proteção de navegador: ele controla quais sites podem chamar, mas o POST em si chega sem autenticação e é barrado antes disso.

A solução que funcionou

  • API Key (header x-api-key): passa pela trava porque a requisição deixa de ser anônima.
  • CORS restrito ao domínio que consome a API, ecoando apenas a origem permitida.
  • Usage Plan: limite de taxa e cota mensal, como proteção contra abuso.
  • O preflight OPTIONS fica sem exigir a chave, para o navegador conseguir validar o CORS.
O trade-off, com honestidade
Quando o cliente da API é um front-end estático (sem backend), a chave precisa viver no navegador para funcionar. O que a protege não é o segredo em si, mas o CORS restrito e o rate limit. O padrão mais seguro (a chave num proxy de backend) vale quando existe um servidor entre o usuário e a API.
MÓDULO 10

Aprendizados para quem lidera

O AI-DLC não é sobre programar mais rápido. É sobre mudar onde o esforço humano é gasto.

Onde o tempo caiu

  • Partida: spec e estrutura saem de uma descrição de intenção, não de dias de setup.
  • Validação: testes gerados junto com o código, então testar deixa de ser o item cortado sob pressão.
  • Integração: CI/CD e o vínculo Jira-GitHub como parte do desenho, com rastro automático entre decisão e código.

Onde o humano continua no comando

  • Calibrar o comportamento da IA (o guardrail em três versões).
  • Decisões de segurança e arquitetura (a trava da conta, a estratégia de exposição da API).
  • A decisão de colocar em produção.
O resumo
Menos tarefa mecânica, mais julgamento. A velocidade de entrega sobe, especialmente na partida. E a qualidade da validação sobe junto. Confirmado em uma aplicação real, um chatbot com knowledge base publicado como API, do intent ao deploy, em poucas semanas de trabalho de fim de tarde.
